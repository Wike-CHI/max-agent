# Route preview (Issue #78, initial slice)

`POST /v1/routes/preview` accepts `{"task_id":"..."}` with the existing bearer token. The task must opt in through `worker_payload.route`, for example `{"unit":"USD","upper_bound":"4","capabilities":["code"],"effort":"high","vendor_pin":"codex"}`. The upper bound is a caller-approved maximum in its original unit, never derived from tokens or mixed with other currencies.

The read-only evaluator orders the owner's accounts by provider/account key and models by model key. It reports stable reason codes for disabled accounts/models, capability and effort mismatch, vendor pin mismatch, closed worker/model binding gates, missing or manually entered price, unit mismatch, and insufficient Global/Provider/Task budget. Preview cannot grant CLI authorization and does not create an attempt, lease, reservation or event. A price source must be an HTTPS source to count as trusted for a paid candidate; configured `manual:` and `fixture:` prices remain visible but rejected.

The current CLI adapter reports the model chosen by the vendor but does not bind a selected model in its execution argv. Consequently the HTTP preview leaves the worker and binding gates closed. Claiming an opted-in task records `route_rejected` before any attempt or paid dispatch; legacy tasks are unaffected. This is intentionally a Draft slice. The remaining #78 work is explicit adapter model binding, a persisted policy-versioned decision with attempt/fence, atomic route and reservation in claim, and measured settlement or reconciliation in finalize/recovery. Preview availability is only a snapshot; the claim must recheck everything in its own transaction.
